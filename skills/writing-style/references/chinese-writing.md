# 中文写作

本参考用于中文技术笔记、博客、README、报告与知识文档。润色、去 AI 味、统一风格或风格审计时，先读 [patterns-chinese.md](patterns-chinese.md)，结合原文判断具体问题。论文任务另读 style-apply.md、paper-voice-contract.md 与 ~/.claude/rules/academic-writing.md。通用表达偏好按 ~/.claude/rules/writing-tone.md 执行。

## 从用途和已有稿件确定写法

先读清这篇文字要让谁了解什么、据此做什么，以及本次允许修改的范围。结合项目要求、原稿和认可样稿判断读者已有的知识，并按当前话题判断，不按身份判断：同一位读者可能熟悉工程实现，却不熟悉某个数学工具；导师了解领域概念，未必了解每个产品的做法。熟悉的共同背景可以略过，新的机制、特有条件和影响判断的差异要讲到读者能用。清晰不等于简化，写给资深读者时不降成入门口吻。材料足够时直接写，只有缺失会实质改变文章方向或成品时才问，不把这一步变成问卷。

动笔前把手头材料分开：读者已有的背景略写或不写；这次的新情况、问题和判断要讲清；只帮助作者理解任务的介绍、讨论和核验经过，不自动进入正文。读者要依靠来龙去脉做判断时，例如交给其他模型审查的材料或决策记录，经过本身就是内容，需要写全。删掉多余的项目介绍或背景后，重新检查其中哪些事实仍在支撑当前问题，把它们留在合适的位置。

参考用户认可的成品时，同时看它选择了什么、解释到哪一步、留下了哪些具体材料。用户亲手改过的版本要与原稿对照，理解增补、保留和删减的作用，再使用它的语气、信息密度和段落节奏。某篇报告的标题、格式或某次删减只在适用范围内沿用。没有同类样稿时，可以用用户当前的自然表达作轻量语气参照，正式程度仍按产物决定。[中文示例](../examples/chinese.md)展示了这些取舍。

不同产物为读者做的工作不同：

| 产物 | 内容与展开方式 |
| --- | --- |
| 调研报告与综述 | 按读者要理解的对象、问题或差异组织材料。具体对象介绍和跨来源综合各有用途；不因读过每份材料就逐份等量介绍。保留用于理解、比较和实际查阅的数字、条件与入口链接。 |
| 技术学习笔记 | 讲清原理、成立条件、推理过程、例子和代价。解释性收束可能正是本节结论，内容需要时可以写长。 |
| 方案与向上汇报 | 从读者关心的真实问题推到方案，让读者理解为什么需要它。相关工作讲清别人怎样做、有什么可取之处，再给出本方案的选择；设计细节集中在本方案部分，按结构展开。结论明确，需要的条件就近说明。读者可能只看图时，图要单独讲清对象、流程和关系。 |
| README 与产品说明 | 从用途讲清做什么、怎样使用和必要条件。操作步骤、配置与接口信息按实际检索需要组织，遵循 writing-tone 的 User-facing Docs 要求。 |
| 测试与操作说明 | 先回答读者要查的问题：测什么、怎样运行、各文件做什么、期望结果是什么，每项写到能用为止。阈值细节、排错步骤和相邻流程是否展开，看读者这次判断或操作是否用得上；只供深入了解的部分给出源文件或文档入口。 |
| 博客与随笔 | 保留作者有来源的观点、情绪和个人节奏。第一人称、经历、幽默与细节来自原文或用户材料。 |

这些是用途判断的参照，不规定章节模板。外部报告、论文和其他模型的意见按用户指定的用途使用；从零起草也不能把概括性观察补成用户的亲身经历或未经提供的具体事例。

## 选择完整内容，再把关系写清

起草或授权重组时，先确定这篇要让读者理解并接受的主线，再决定哪些事实、论证、条件和例子帮助读者完成本次阅读目的，并安排它们的位置。材料中重复的背景可以合并，能说明核心区别的内容展开到读者理解为止。平均用力同样会让重点消失：各对象都有的功能用一两句合并交代，篇幅留给区分对象的特点和读者缺少的机制，不为共性功能逐个点名产品。细节放在承担它的位置：总述与相关工作讲做法和取舍，本方案或方法部分承载设计细节；读者当前阶段用不到的实现细节不提前展开。读者需要的产品入口、引用与关键数字也是内容；采集过程、内部记录和修订历史按其用途放在工作材料或交回说明里。正式成品中不写“待确认”“未核实”一类核验状态：能核实的先核实；影响判断的不确定性用自然语言说明依据的范围，作者尚未查到的事项放在交回说明。

形式按内容之间的关系选择，一篇文字可以组合使用：命令、文件用途、字段和同维度比较用便于查阅的清单或表格，推理、概念讲解和思考脉络用连贯段落。两种失败都要避免：把有主线的内容切成互不相连的短点，或把需要查阅的内容写成逐行阅读的解释。去掉装饰性的加粗、标签和符号之后，仍按内容关系决定形式，不默认改成段落。

润色保留原文的事实、数字、论证、比较条件、例子、现场细节、作者立场与不确定性。删除前问“读者会少知道什么”：会少知道理解对象、论证或判断所需的内容，就应保留或换一种表达。保留或增加解释、限定与比较时，也要问“这句话帮助读者理解哪个事实、判断或关系，或作出什么决定”。需要可以来自读者的问题、实际歧义和上下文，不必先写成一个单独的论断。

只交代本文没有讨论、证明或声称什么，却不影响当前判断和阅读用途的自我说明，可以在润色时去掉；不能因此删去真实反证、必要范围或作者的不确定判断。草稿中已有这类句子，也要核对其作用。若删除会改变主张、证据关系或作者立场，就按实质内容修改处理；只改指定字句的任务保持其余内容原样。空话可以删，含糊表述优先用上下文已经给出的具体事实写清；没有可替换的事实时，保留原信息及其真实程度，不补造数据，也不用删除代替修复。

先修影响理解的问题。让读者尽早知道谈论的对象、动作和条件，再展开新的机制或结果。名词堆叠、长定语和多层从句使关系难读时，调整主语、信息顺序或分句；必要的范围与因果仍附着于原来的判断。“是”“有”及被动句可以准确说明身份、存在或受影响对象，不为改变句形强行替换。

段落从读者已经理解的内容接到新的说明。判断相邻句段是在展开、比较、举例、转折、推导还是描述先后，再选用能够表达该关系的措辞。指代不清时点明对象；只有一个明确前项时，代词即可承接。连接词不能弥补实际缺失的关系，也不因出现频繁就删除。必要条件贴近它所限定的判断，解释完成后自然结束，不顺带枚举尚未处理的其他问题。

句子长度随内容变化。长句可以保留完整关系，短句可以突出明确事实；重复的句法确实让阅读生硬时再调整。技术术语保持一致，不为制造变化循环换同义词。数据需要解释时，把观察与解释的关系写清；事件需要过程时，交代触发、执行、结果和处理。句长分布、段落数量与字数减少都不能证明质量变好。

## 按当前请求完成修改

指定增删落实到对应位置，保持无关正文原样。轻量润色保留作者措辞，只修具体表达问题；通顺的句子可以不动。已有草稿不自动把任务限制成逐句微调，要求重组时就在授权范围内重新安排完整内容。

涉及事实、含义、论证或结构的实质纠正时，执行 Core Rule 7：先列出仍需保留的事实、论证、条件、例子、细节与作者立场，对照受影响的原段落或章节核全，再据此重写，最后同时对照清单与原件检查。内容较长或已多轮实质纠正时，读取 long-form-humanize.md，在不携带修订史的干净上下文中，用确认后的要求、完整保留内容和原始材料重新写出受影响部分。检查同类问题与相邻衔接，修正授权范围内的实例。

用户的短确认承接当时提出的做法，不自动改变更早的明确要求。保留当前任务中已经选择的用词与语气；原稿的自然痕迹不需要被统一抹平，也不为显得像人而添加笔误、口头禅或情绪。技术身份、事实和会改变含义的错误仍按本次任务处理。

用户要求“只标不改 / detect / audit”时，报告问题位置、原文和具体影响，不改写，也不据句式判断作者身份。

## 读完结果，再交付

按受影响的段落或章节对照原件，核对有效信息是否保留，关系与结论强度是否准确。读完整结果，检查必要定义、指代、前后衔接和同一概念的用词，也检查是否为未提出的判断多加了一层辩护；确认没有为了平实而省掉推理，也没有为了具体而增添原文没有的事实。

成稿再对照原始用途、明确排除项和长度要求。用户只要正文时直接交正文，写作过程、结构说明和自我评价留在需要的交回消息里。完成所有授权修改，交付可直接使用的正文、文件或 diff。

术语按目标读者和用户既定写法处理：读者需要时在首次出现处解释，领域内熟悉的缩写直接使用；中文译法不稳定时保留英文，全文保持同一写法。标点与强调服从既定偏好和体裁，用户全局的破折号禁令继续生效。
