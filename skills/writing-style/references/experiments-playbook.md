# 实验与分析写法

目标：让读者确信结果是**真实的**、**公平的**、**可解释的**。

## 推荐结构

### 1) 实验设置

必须明确说明：

- **数据集**：来源、规模、划分方式、预处理
- **评测指标**：指标定义 + 为何选择该指标
- **对比基线**：每个基线的简要描述 + 选择理由
- **模型配置**：参数设置、API调用方式、采样策略
- **实验环境**：硬件配置、软件版本（如涉及性能评测）

### 2) 主实验结果（锚点表格）

- 主结果表是本章核心，用于回答"本文方法有效吗"
- caption 自包含（读者只看表也能理解）；最佳结果**加粗**；表注说明缩写和特殊标记（规范见 `figures-and-tables.md`）
- 表格首次被正文引用时说明指标的计算口径（如 pass@k 的估计方式与 k 取值）

### 3) 分析（超越"谁赢了"）

至少包含以下一项：

- **消融实验**：每个组件→预期效果→实际效果
- **失败分析**：失败案例分类 + 原因探讨
- **敏感性分析**：关键参数的影响
- **定性分析**：典型成功/失败案例展示

### 4) Takeaway 与主要发现

**结果簇的叙述形状**：每个实验簇（共享基线/指标的一组结果）开头先点明它回答哪个 claim 的哪个疑问，中间给数字和具名的具体实例，展示完毕立即用 1-2 句有界 takeaway 说明读者可以相信什么、回扣该 claim。不等所有结果展示完才总结。簇与簇按 claim 的依赖关系排列：先立现象，再看主效应，机制与边界放在后面。

**End-of-section 主要发现**：全章结尾用总结句 + 编号列表呈现核心发现：

> 实验结果表明：
>
> (1) ……（具体观察 + 数字 + 基线对比）
> (2) ……
> (3) ……

### 5) 讨论与局限

- 承认结果的局限性
- 指出可能的改进方向
- 比笼统的"未来工作"更具体

### 6) 实验完备性检查

以下维度是审稿人最常检验的完备性缺口，在实验设计阶段补齐，比写作阶段辩解有效：

| 常见质疑 | 预防策略 | 写作体现 |
|----------|----------|----------|
| "基线不够强/不公平" | 至少包含一个公认强基线（如该领域 SOTA 模型）；对比条件（prompt、采样次数、温度）保持一致 | 实验设置中明确说明基线选择理由和统一配置 |
| "实验不可复现" | 提供随机种子、模型版本、API 参数、运行命令 | 设置节列出完整配置；附录或仓库提供复现脚本 |
| "消融实验缺失" | 消融组件与贡献点一一对应，而非随意拆卸组件 | 每个消融项对应一个贡献点，说明"去掉X后Y指标下降Z%" |
| "数据集太小/覆盖不全" | 主动说明数据规模的合理性（如"覆盖了N个平台的M道题"） | 数据集描述中给出规模、来源分布、与现有基准的对比 |
| "与现有工作对比不充分" | 确保最接近的工作被直接比较，而非仅引用 | 主结果表中包含最接近工作的数据，讨论中分析差异原因 |
| "统计显著性不足" | 多次运行取均值/标准差；差异不大时诚实标注 | 结果表标注方差或置信区间；文字中用"接近""差异不显著"等表述 |

## 结果描述措辞

### 强结论（数据支撑充分）

- "实验结果表明，……"
- "与基线X相比，本文方法在指标Y上提升了Z%"

### 弱结论（趋势性观察）

- "初步表明……"
- "可能与……有关"
- "有待进一步验证"

### 差异不显著

- "两者表现接近，差异不具有统计显著性"
- 不要回避负面结果，诚实分析更有说服力

## 自查清单

- [ ] 实验设置完整（数据+指标+基线+配置）
- [ ] 主结果表存在，caption 自包含
- [ ] 有超越"谁赢了"的分析（消融/失败/敏感性）
- [ ] 每个实验簇后有 per-cluster Takeaway（回扣 claim）
- [ ] 全章末有总结性主要发现列表
- [ ] 结果描述措辞与证据强度匹配
- [ ] 负面结果被诚实报告
- [ ] 局限性被具体说明
