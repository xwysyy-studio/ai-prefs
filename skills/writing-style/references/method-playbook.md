# Method 写法（top venue）

Method 的组织单位是论证：核心 insight 在每一环要求模型、系统或 benchmark 做到什么，哪个机制承担了这一环。展开顺序跟着 insight 的逻辑走，读者先知道为什么必须有这一设计，随后才看到输入、操作和输出。

正式组织小节与公式前，先用几句大白话讲清完整流程：输入是什么，每一步处理什么，输出是什么，以及各步为什么按这个顺序出现。读者仅凭这段说明就应能复述方法；公式和术语随后负责精确表达。

一个方法小节按四步展开：

1. 点明它兑现 story 的哪一部分（这一环必须做到什么）
2. 给出机制与必要定义
3. 说明该机制改变了什么可观察行为
4. 交代它不负责什么

**独立贡献测试**：删掉某个模块后，论文的一句话 story 原封不动，这个模块就按实现细节处理，收进所属小节或附录。

Benchmark / dataset 论文的 design rationale 按同一原则写：先说这个设计把什么原本混在一起的对象区分开、把什么变得可测，再写数据结构、指标和协议。

## 写作细则

- 章首概述段指向架构图；架构图在本章出现且被正文引用
- 公式、算法前有文字说明；符号在首次使用处定义（符号规范见 `equations-and-notation.md`）
- 设计决策给理由（"选用 X 是因为……"）
- 术语约定：核心概念首次出现给全称与缩写，此后只用一种叫法，不交替使用近义词
- 聚焦设计思路和关键决策；代码片段（如有）放附录

## 自查清单

- [ ] 每个方法小节能指认它兑现 story 的哪一环
- [ ] 每个模块有功能定义与设计理由
- [ ] 公式符号定义在首次使用处
- [ ] 无孤立图表（每张图/表在正文中被提及）
- [ ] 通不过独立贡献测试的模块已降级为实现细节
