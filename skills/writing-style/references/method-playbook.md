# 系统设计/方法写法（中文学术）

目标：让读者**理解设计思路**、**看到系统全貌**、**把握关键技术**。

本科毕设通常以系统设计为核心（非纯理论推导）。不少论文会将“系统设计”和“系统实现”拆成两章，本 playbook 同时给出两者的写法建议。

## 推荐结构

### 1) 概述（1段）

- 本章目标 + 与上章衔接
- 指向系统架构图（"如图X-1所示"）
- 高层概括系统由哪些模块组成

**模板：**
> 基于第2章的分析，本章设计面向交互算法题的评测系统。图3-1展示了系统总体架构，主要包含数据构建、交互评测引擎、多模型代码生成、诊断分析与可视化四个子系统。下面依次介绍各子系统的设计。

**术语约定提示：** 建议在系统设计章开头插入一段术语约定（模板见 `terminology-and-citation.md` 的"术语约定段落模板"），统一全文核心概念的称谓。

### 2) 系统总体架构（0.5-1页）

- 架构图是锚点，必须出现
- 说明各模块的职责和模块间数据流
- 不展开细节，只给全景

### 3) 各模块详细设计（每模块1-2页）

每个模块的写法：

1. **功能定义**：该模块做什么（1-2句）
2. **设计思路**：为什么这样设计（选型理由）
3. **关键技术**：核心算法/流程（可含伪代码、流程图）
4. **输入输出**：接口定义

### 4) 关键算法/公式（按需）

- 公式前先用文字解释直觉
- 公式后解释每个符号
- 编号格式：(章-序号)，如 (3-1)

**模板：**
> 本文采用 pass@k 的无偏估计公式计算通过率：
>
> pass@k = E[1 - C(n-c, k) / C(n, k)]  (3-1)
>
> 其中 n 为总采样数，c 为通过的样本数，k 为选取数量。

### 5) 实现要点（可选，0.5-1页）

- 编程语言、框架选型
- 关键第三方库及版本
- 部署环境

### 6) 系统实现章节（对应独立“系统实现”章，工程性写法）

推荐写法：**先运行闭环，再展开模块实现**。

1. **开发环境与技术选型**：语言/框架/关键依赖版本（与代码仓库一致）
2. **代码结构与模块映射**：用一张表把"设计章模块"映射到"实现章模块/目录/接口"
3. **关键流程落地**：用流程图说明一次评测任务从输入到输出的执行路径（含异常分支）
4. **可复现性与部署**：运行命令、配置项、日志/结果目录结构（避免贴大段代码）

**各子系统实现要点参考**（与 `../soul.md` 四子系统对应）：

| 子系统 | 设计章重点 | 实现章重点 |
|--------|-----------|-----------|
| 数据构建 | Propose-Validate-Adjudicate 流水线设计 | 爬取/清洗脚本、数据格式规范、质量校验流程 |
| 交互评测引擎 | 双进程 cross-pipe 通信 + 资源沙盒 + verdict 判定 | 进程管理实现、超时/异常处理、判定状态机 |
| 多模型代码生成 | 统一 API 适配层 + 批量调度策略 | API 封装、并发控制、重试与错误处理 |
| 诊断分析与可视化 | pass@k 计算 + failure taxonomy + 展示方案 | Web 前后端实现、数据聚合逻辑、可视化组件 |

## 写作原则

### 先意图后细节

- 每节先说"为了实现X"，再说"采用了Y方法"
- 避免直接跳入代码/算法而不解释目的

### 图文配合

- 每个主要模块至少一张图（架构图/流程图/示意图）
- 图在文中必须被引用
- 不要放了图不提，也不要提了图不放

### 避免过度实现细节

- 本科毕设常见问题：把代码截图当"设计"
- 应聚焦设计思路和关键决策，非逐行代码
- 代码片段（如有）放附录

## 自查清单

- [ ] 公式/算法前有文字说明
- [ ] 公式符号定义在首次使用处
- [ ] 设计决策有理由（"选用X是因为……"）
- [ ] 无孤立图表（每张图/表在正文中被提及）
